# RV32I solver and verification

## Build and run

```sh
make run-rv32
make run-rv32 RV32_STATE=25314672313211
make run-rv32 RV32_STATE=21345671111111 RV32_PROC=RV32_5S
```

`make rv32` builds only. Requires Make and `riscv64-unknown-elf-gcc`,
`riscv64-elf-gcc`, or `riscv32-unknown-elf-gcc`; override with `RISCV_CC`.
The Makefile finds Ripes in PATH or common macOS application directories;
override `RIPES` with the executable path if necessary. Ripes must provide
`RV32_ISS`. No Python is used.

The normal build compiles `rv32/tables.c` into `tables.o`, assembles
`solver_rv32.S`, and links both using `rv32/link.ld`. The table object is reused
until its source, header, or Makefile changes. Changing only the input rebuilds
the small assembly program. The `.S` suffix enables the C preprocessor but
does not make C array declarations valid assembly: `tables.c` includes the
original `pdb_table.h`, and assembly accesses the linked arrays through
exported addresses. No table conversion is needed.

For Ripes GUI with LEDs:

1. In **I/O**, double-click **LED Matrix** to create **LED Matrix 0**.
   Set **Width=35, Height=25** (Height is listed first).
2. Run `make rv32-gui`, optionally adding `RV32_STATE=...`.
3. In Ripes, use **File → Load Program → Executable (ELF)** to open
   **`build/rv32/solver-led.elf`**. Choose the five-stage processor with
   forwarding and hazard detection; disable M/C extensions.
4. Float the LED window with its undock button, then **Run (F8)**. The display
   starts at the input and updates after each move from the actual solution.
   Floating the window also avoids stale painting in the embedded I/O view
   observed on this macOS build. Use **Reset (F3)** to replay.

Ripes automatically exports the peripheral symbols in `$TMPDIR/ripes_system.h`
(or `/tmp/ripes_system.h` on systems without TMPDIR). The GUI target includes
that header and caches it under `build/rv32/`, because a CLI Ripes process clears
the shared header. Override `RIPES_IO_HEADER` if necessary. Rebuild after
changing peripherals; the ELF uses the addresses exported at build time.
No address is hardcoded in the renderer. `RV32_RENDER_DELAY` controls visual
pacing (default 40,000 loop iterations); it never affects CLI measurements.

`make rv32` and `make run-rv32` compile the renderer out (`RENDER=0`). You may
also load `build/rv32/solver.elf` in GUI for pipeline inspection. The assembly
editor alone cannot link the separate table object. Rebuild and reload the
ELF to change inputs.

`make check-led` validates the renderer ELF's actual color/net tables against
an independent geometric oracle: 1,512 sticker rotations, all nine moves,
golden nets, RGB24, color counts, the fixed corner, and inverse recovery.
The GUI ELF has 2,368 bytes of text and 118,596 bytes of static data.

## LED mapping

The face order is U,L,F,R,B,D. U is white, L orange, F green, R red, B blue,
and D yellow. Four LEDs across and three down represent one facelet. Face
origins are U=(9,0), L=(0,7), F=(9,7), R=(18,7), B=(27,7), D=(9,14).
The net occupies 35 by 20 LEDs, leaving five bottom rows black. Separator
columns and rows stay black; all writes use `BASE + 4*(y*WIDTH+x)`.

Physical cubies 0..7 have ordered face triples `(U,F,L)`, `(U,R,F)`,
`(D,F,R)`, `(D,L,F)`, `(U,B,R)`, `(D,R,B)`, `(D,B,L)`, `(U,L,B)`.
At a face slot k, the color index is `(k + orientation) mod 3` in the
occupying cubie's triple. Corner 0 is fixed; moving corners use internal
array index corner-1. This orientation convention matches R/B/D geometry.
The renderer preserves the input separately because target solution replay
mutates the verification cube to solved. Each emitted move advances the
display state by one, two, or three quarter turns and redraws all facelets.

For `21345671111111`, the output is:

```text
R B' D2 R' B R' B' R D2 R B
```

A solved input prints an empty line. Exit status is 0 for success, 2 for
invalid input, and 1 for search or verification failure. Ripes appends its
own exit message. `solution_length`, `search_nodes`, and `test_status` are
available as symbols for inspection.

## 1. Baseline and state space

Fix one corner's position and orientation to remove whole-cube rotations.
The remaining seven cubies have `7!` permutations. Their twists are elements
of Z/3Z with sum zero, leaving six independent digits and `3^6` orientations.
Thus the group generated by R, B, and D has order `7! * 3^6 = 3,674,160`.
The twist constraint is modulo 3; it is not a permutation-parity test.

The Cayley graph uses nine unit-cost generators: R/R2/R', B/B2/B', and
D/D2/D'. A half turn costs one move. Independent host BFS reaches every state:

| Distance | States | Distance | States |
| ---: | ---: | ---: | ---: |
| 0 | 1 | 6 | 50,136 |
| 1 | 9 | 7 | 227,536 |
| 2 | 54 | 8 | 870,072 |
| 3 | 321 | 9 | 1,887,748 |
| 4 | 1,847 | 10 | 623,800 |
| 5 | 9,992 | 11 | 2,644 |

The nonempty final level gives a lower bound of 11; exhausting the entire
domain without a deeper level gives the matching upper bound. This agrees
with the independently published [Pocket Cube distribution](https://www.jaapsch.net/puzzles/cube2.htm).

The original hosted BFS baseline needs 14,696,640 queue bytes, 3,674,160
move-table bytes, and 34,614 factored-transition bytes: 18,405,414 bytes for
those three allocations alone. It expands 33,067,440 edges and performs
66,134,880 factored transitions. The assignment's order-of-1e9 instruction
estimate is a projection, not a measurement of running that baseline here.
Keeping the complete result as a verification artifact is useful on the
host; it exceeds the target's 128 KiB data budget even with nibble packing.

### Measured simulator cost

`make probe-rv32` runs a memory loop in fresh Ripes processes. Every case
performs 1,048,576 word stores, varying only the touched span: 4 KiB, 1 MiB,
2 MiB, and 4 MiB. There are three repetitions per span and model.
`wait4().ru_maxrss` measures peak process RSS in bytes on macOS; Linux values
are converted from KiB. The summary fits a line with an intercept to the four
median RSS values. This estimates incremental host bytes per guest byte,
rather than dividing process startup overhead by a tiny guest allocation.

The loop has `5*N + floor(N/words) + 13` retired instructions, verified on
both models. Rates use Ripes' `--exectime`; the TSV also records elapsed
wall time including startup. The 4 KiB median rate projects time for 1e9
instructions. It is an optimistic small-working-set estimate, not a prediction
that BFS has the same instruction mix or memory locality.

Measured medians (RSS in bytes):

| Touched span | ISS RSS | Five-stage RSS |
| ---: | ---: | ---: |
| 4,096 | 73,351,168 | 120,700,928 |
| 1,048,576 | 131,547,136 | 161,087,488 |
| 2,097,152 | 191,627,264 | 203,309,056 |
| 4,194,304 | 311,640,064 | 260,505,600 |

| Derived quantity | RV32_ISS | RV32_5S |
| --- | ---: | ---: |
| Host bytes / additional guest byte | 56.946 | 33.258 |
| Fitted fixed overhead, bytes | 72,486,551 | 125,338,238 |
| Increment for 18,405,414 guest bytes | 1,048,116,495 | 612,125,031 |

Raw repetitions and the fitted summary are in `build/rv32/probe/`. These
measurements finished with no other test simulations running. The larger
span rates range from 17.25 to 22.60 million instructions/s for ISS and from
272,655 to 285,048 for the five-stage model. A fast ISS on this host does not
remove the static-data limit or the much slower visual pipeline execution.

The pinned [VSRTL address space](https://github.com/mortbopet/VSRTL/blob/8497dd14fe80e57efcff4c424a9a3b6363d93eb7/include/VSRTL/core/vsrtl_addressspace.h)
stores guest bytes in a hash map. The measured slope includes allocator and
container overhead and is specific to this binary and machine. Extrapolating
beyond 4 MiB assumes similar allocation behavior; rehashing can change it.

## 2. Representation, search, and memory budget

The target stores full permutation `p` in 0..5039, orientation `o` in 0..728,
and the ordered positions of cubies 0, 1, 2 as `pp` in 0..209. The heuristic
is `max(perm_dist[p], PDB[o, pp])`. The second abstraction retains all
orientations and those three positions, forgetting the other cubie identities.

Every real move projects to an abstract move of the same cost. Projecting
any solution therefore gives an abstract path no longer than that solution.
Both abstract distances are lower bounds, and their maximum remains a lower
bound. Adding them would require a separate cost-partitioning argument, so
this implementation uses the maximum. H1 verifies the inequality everywhere.

Iterative deepening begins at the root heuristic and increases the bound
through 11. At depth `g`, a node is pruned only if `h > bound - g`.
Consecutive turns of one face can be merged or canceled, so omitting them
cannot remove a shortest solution. Each bound has a finite search tree;
the first successful bound is optimal, and the independently established
diameter guarantees termination by 11 for valid inputs.

| Table | Entries and width | Bytes |
| --- | --- | ---: |
| `perm_q` | 3 * 5,040 * uint16 | 30,240 |
| `ori_q` | 3 * 729 * uint16 | 4,374 |
| `pp_q` | 3 * 210 * uint8 | 630 |
| `perm_dist` | 5,040 * uint8 | 5,040 |
| `pdb_table` | 729 * 210 nibbles | 76,545 |
| **Table contents** | | **116,829** |

The assembly ELF contains `.text = 1,836`, `.rodata = 117,092`, `.data = 0`,
and `.bss = 1,344` bytes. Static data totals **118,436 bytes**, including
all descriptors, strings, replay buffers, 768 bytes of search frames, and
a 512-byte reserved stack. This leaves **12,636 bytes** below 131,072.
The linker asserts this limit. There is no target heap, recursive call chain,
floating point, or complete-state distance table. Section-address gaps are
not allocated static data.

Host BFS validation tables stay in the native checker. Neither their
distances nor their solution paths are linked into the target solver.

## 3. Existing C improvements

The final C algorithm is retained. Quarter-turn transition tables replace
per-child cubie permutation and orientation arithmetic. Repeating a face's
quarter transition enumerates its three nonidentity moves, avoiding nine
separate transition rows. The orientation/partial-permutation PDB needs
153,090 nibbles instead of an entry for every complete state.

Lehmer ranking uses 21 pair comparisons and Horner factors 6, 5, 4, 3, 2.
Constant shifts/adds implement those factors, base-three orientation ranking,
and the partial rank `30*a + 5*b + c`. The packed lookup uses byte offset
`105*o + (pp >> 1)`, where `105 = 64 + 32 + 8 + 1`, then selects a nibble.
These operations avoid variable multiplication/division on RV32I. Validation
and replay reduce twist sums with one conditional subtract: the sum of two
reduced twists is at most four.

The native solver changes in this update only add compilation guards for
the freestanding reference; its search and table contents are unchanged.

## 4. RV32I translation and measured comparison

`solver_rv32.S` implements parsing, ranking, iterative search, output, and
independent cubie replay. It links without startup libraries or arithmetic
helpers. The checker decodes every executable word and rejects instructions
outside the emitted RV32I subset. Compiler flags are
`-march=rv32i -mabi=ilp32 -mno-relax`.

`ida_solve(a0=p, a1=o, a2=pp, a3=path)` returns signed length in `a0` and node
count in `a1`, preserving callee-saved registers. Valid ranks and an 11-byte
path buffer are preconditions. It makes no calls and uses an 80-byte call
frame. Static search frames make it non-reentrant.

`s0` is a 64-byte frame cursor, `s1` is remaining depth, `s2` is the bound,
`s6` is the path cursor, and `s9`..`s11` hold the coordinates. Parent and
candidate coordinates, move cursors, and table pointers remain in each frame.
Moving the frame pointer by 64 replaces repeated C array indexing and
entered-node flags; hot coordinates stay in registers.

Both assembly variants retain the same traversal and pruning condition.
`RV32_EARLY_PERM=0` calculates both components and their maximum. The default
checks permutation distance first, skipping the packed PDB lookup if it
already exceeds the remaining depth. This saves its address calculation,
load, and nibble extraction on rejected nodes without changing the answer.

`rv32/reference.c` compiles the **full final C algorithm**: input parsing,
validation, coordinate ranking, search, and answer formatting. Only argv and
stdio are adapted to inline input and Ripes ecalls. Both versions share
startup, exit, and the independent assembly replay. This is a freestanding
algorithm comparison, not a comparison with hosted libc. GCC uses
`-O2 -ffreestanding`; its one static call frame is 272 bytes and fits the
512-byte reserve. The Makefile audits the stack-usage report.

| Input | Assembly: maximum | Assembly: early check | Full C, GCC -O2 |
| --- | ---: | ---: | ---: |
| `12345671111111` | 555 | 555 | 726 |
| `25314672313211` | 1,430 | 1,400 | 1,747 |
| `21345671111111` | 1,825,539 | 1,629,349 | 2,914,480 |
| `12347651111111` | 7,867,986 | 6,862,920 | 12,553,151 |
| Linked `.text` bytes | 1,840 | 1,836 | 2,320 |
| Static data bytes | 118,436 | 118,436 | 117,608 |

These are measured `RV32_ISS --iret` counts including assertions and replay.
For the worst distance-11 input, early rejection reduces instructions by
12.77% relative to the maximum variant. C still evaluates both components,
so the early-check comparison also includes that optimization. These retained
variants are reproducible comparisons, not invented historical commits.
Existing commits `fecee00`, `56894a5`, and `a28d4fc` record the table, C search,
and host-gate work. The current source retains both assembly variants so the
comparison can be reproduced.

`make bench-twist` compares conditional twist reduction with the retained
`BRANCHLESS_TWIST=1` experiment on both models. All twelve queries passed.

| Input | ISS iret: conditional / branchless | Five-stage cycles: conditional / branchless |
| --- | ---: | ---: |
| Solved | 555 / 555 | 725 / 725 |
| Short, `25314672313211` | 1,400 / 1,429 | 1,787 / 1,800 |
| Required, `21345671111111` | 1,629,349 / 1,629,530 | 1,997,307 / 1,997,420 |

Branchless uses four instructions after the twist addition, versus two or
three for the conditional reduction, and increases text by four bytes.
It also loses in total pipeline cycles for these inputs, so conditional
reduction stays the default. Search uses orientation tables; this reduction
is in the short independent replay. Raw results are in `build/rv32/twist/`.

## Verification results

```sh
make check-rv32       # Assembly and full-C regression, ISS and five-stage
make check-rv32-all   # H1-H4, then ALL 2,644 distance-11 states in Ripes
make bench-rv32       # Three linked variants on four cases
make probe-rv32       # RSS and simulation-rate measurements
make verify-rv32      # All of the above, sequentially, plus environment record
```

Only verification needs a native C compiler. `tests/check_rv32.c` reuses the
independent cubie/BFS oracle in `tests/check_gates.c`; it invokes actual Ripes
rather than implementing another emulator. On macOS it selects a matched
Command Line Tools compiler/SDK without changing system Xcode settings.
`RV32_HOST_CC` and `RV32_HOST_FLAGS` override that choice.

H1-H4 passed over all **3,674,160 states**. H3 ran every C query, verified
optimal length, and replayed each path in **20 seconds** in the recorded run.
Maximum heuristic is 9; permutation distance maximum is 7. H4 checks all
76,545 low-nibble and 76,545 high-nibble entries against unpacked distances.
Results are in `build/rv32/gates-current.log`.

Each target regression passes 42 valid states, including 32 deterministic
pseudorandom states, and 10 invalid inputs. Twelve valid cases also pass on
`RV32_5S`, including solved, one-move, required eleven-move, and worst
inputs. A deliberately wrong expected length is rejected on the target,
confirming that the assertion executes. Both assembly and full C pass.

The exhaustive target run passes **all 2,644 distance-11 states**:

| Statistic | RV32_ISS retired instructions |
| --- | ---: |
| Minimum, `73516243323113` | 318,832 |
| Mean | 912,810.60 |
| Maximum, `12347651111111` | **6,862,920** |
| Required vector, `21345671111111` | **1,629,349** |
| Per-state limit | 50,000,000 |

Target enumeration took **420.364 seconds**, excluding initial host BFS.
Every result had length 11 and passed replay inside the target and on the
host. The largest count is 13.73% of the limit. This certifies the distance-11
set, not exhaustive RV32 execution of all 3.67 million inputs. The all-state
H3 run is a separate native C test.

For each query the checker copies the linked ELF and patches only named
`input_state` and `expected_length` data symbols. Instructions and tables are
unchanged. Normal builds set expected length to -1 and skip the comparison;
the enabled check costs one additional assembly instruction. Consequently
plain `make run-rv32` reports **1,629,348** for the required vector.
In these solver runs the pinned five-stage model reports one fewer retired
instruction than ISS at termination; use the required ISS metric for the
budget and retain each model's raw telemetry.

Reports, ELF copies, TSVs, stdout/stderr, and Ripes JSON telemetry stay under
ignored `build/rv32/`. Failed subprocesses, missing telemetry, nonzero target
status, wrong lengths, replay failures, and budget violations fail the checker.
macOS process-policy warnings on stderr are kept separate from move output.

## Pipeline walkthrough

Choose the five-stage processor's **Extended** layout. Enable **View → Show
processor signal values**, or right-click a port and choose **Show value**.
Use **Clock (F5)** and the stage table to track instructions. The default
layout hides some control wiring.

Actual GUI captures were recorded on October 7 using the renderer-free ELF
with input `21345671111111`. The startup/parser sequence demonstrates:

| Cycle | Observed behavior | Capture |
| ---: | --- | --- |
| 5 | `addi sp,sp,-336` in WB; ALURES=1, register write enabled to x2, result `0x2ceb0` | [Arithmetic](images/pipeline-arithmetic.png) |
| 15 | `lbu t3,0(a0)` in EX, dependent `addi` in ID; front end held and bubble requested | [Load-use stall](images/pipeline-load-stall.png) |
| 17 | Load in WB selects MEMREAD=0; WbStage=2 forwarding supplies `0x32` to EX, which computes `0x32-49=1` | [Forwarding](images/pipeline-load-forwarding.png) |
| 25 | `sb t3,0(a1)` in MEM; write enabled, address `0x2cc70`, data 1; Memory still shows Byte 0=0 | [Before store](images/pipeline-store.png) |
| 26 | Store in WB has register write disabled; refreshed Memory shows Byte 0=1, neighboring bytes unchanged | [After store](images/pipeline-memory-after.png) |

At cycle 5, x2's new value is on the writeback input and commits on the next
clock edge. In the cycle-25 screenshot the register write enable belongs to
the older `or` in WB; the `sb`'s no-register-write control is visible at cycle
26. Stage occupancy determines which instruction each enable describes.

The Memory table retained its old display immediately after stepping.
Selecting **Go to section → Address... → 0x2cc70** again refreshed it without
advancing the processor. This address is the CLI ELF's linked `cube` symbol;
inspect symbols again after rebuilding, especially for the LED ELF.

The following separate source-based example in `search_turn` is not the
instruction pair shown in the startup/parser captures:

```asm
lhu s9, 0(t0)
sw  s9, 20(s0)
```

`t0` points to `perm_q[face][candidate_p]`; the loaded value is the new
permutation coordinate. Storing it in the parent frame ensures the next
turn of that face starts from the correct candidate.

| Stage | `lhu` | `sw` |
| --- | --- | --- |
| IF | Fetch at PC; ordinarily select PC+4 | Fetch the following instruction |
| ID | Read base `t0`, decode unsigned halfword load | Read base `s0` and data `s9`; detect load-use dependency |
| EX | ALU adds base and immediate 0 | After the stall, add base and immediate 20; forward loaded store data |
| MEM | Read two bytes and zero-extend | Write four bytes of the coordinate at `s0+20` |
| WB | Select memory result; enable write to `s9` | Register write enable is zero |

`alu_op2_src.select = IMM (1)` for both instructions. `reg_wr_src.select =
MEMREAD (0)` supplies load writeback, and `memwb_reg.reg_do_write_out` enables
it. For the store, `exmem_reg.mem_do_write_out` enables data memory and no
register is written. A load in EX with its consumer in ID drives
`hazardFEEnable = 0` and `hazardIDEXClear = 1`: PC/IF-ID hold and a bubble is
inserted. After the load progresses, forwarding supplies the store data.
Arithmetic writeback selects `ALURES (1)` instead of memory.

The later `sb t1, 0(s6)` writes one path byte: `3*face + turn` in 0..8.
Advancing the frame decrements remaining depth; backtracking restores parent
coordinates. The completed path is independently replayed before printing,
tying these local memory updates to the final solved cube.
